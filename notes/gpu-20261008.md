# Mali-G57 GPU for Hyprland, 2026-10-08: ChromeOS's own libmali

Result: Omarchy's Hyprland renders on the Mali-G57 (OpenGL ES 3.2, ARM r54p1) instead of llvmpipe. Hyprland
idles at ~5% CPU (llvmpipe peaked ~400%), no kbase faults, and the user reports it feels smooth.

## Why libmali first, not the phone's Mesa/kbase

- The kernel's kbase is `r54p1-12eac0`, and it already rewrites the GPU ID (`Detected G-57 variant with GPU ID
  90930010. Changing the ID to 90910010`) to the product Arm's Linux DDK expects (the mismatch the phone had to
  binary-patch).
- ChromeOS ships the exactly matching userspace: `/usr/lib64/libmali.so.0.54.1` (`r54p1-12eac0`), a glibc build
  whose only extra dependency is libc++. Copied from this machine's own ROOT-A (`/dev/sda3`, mounted read-only);
  not redistributed.
- The phone's patched Mesa (panfrost-kbase from RandomCoderOrg/mesa-gfxstream, JM UAPI 11.38) stays the fallback;
  it would need checking against the r54 UAPI.

## Making it load on Arch

1. **`DT_RELR without GLIBC_ABI_DT_RELR dependency`**: ChromeOS links with RELR relocations but its glibc does not
   require the `GLIBC_ABI_DT_RELR` version need that upstream glibc (>= 2.36) checks for.
   [`scripts/patch-cros-relr.py`](../scripts/patch-cros-relr.py) adds that requirement under `libc.so.6`
   with LIEF (hash `0xfd0e42`, matching Arch's `libc.so.6` definition) into a new file
   `libmali.so.0.54.1.relr`; the original is kept in `/opt/quigon-gpu/mali/orig/`.
2. libc++/libc++abi: Arch's `libc++` 23 instead of ChromeOS's copies (same RELR problem otherwise).
3. Prefix `/opt/quigon-gpu/mali/lib`: `libmali.so.0 -> libmali.so.0.54.1.relr`, and `libEGL.so.1`,
   `libGLESv2.so.2`, `libGLESv1_CM.so.1` all pointing at it (libmali exports all of EGL/GLES itself).
   System Mesa is untouched.

[`bringup/mali-probe.c`](../bringup/mali-probe.c): EGL 1.5 vendor ARM, GL_RENDERER `Mali-G57`, GLES 3.2,
FBO clear/readback PASS, **mediatek-drm dumb buffer → PRIME DMA-BUF → EGLImage render target: 300/300 frames
pixel-exact, 1.02 ms per 1920×1200 clear**. Display extensions include `EGL_EXT_image_dma_buf_import(_modifiers)`,
`EGL_KHR_surfaceless_context`, `EGL_KHR_no_config_context`, `EGL_ANDROID_native_fence_sync`, `IMG_context_priority`.

## Making Hyprland accept it

libmali's only client platform is the default display (`EGL_EXT_platform_base`, no GBM/Wayland/device platform),
while Hyprland 0.56 needs `EXT_platform_device` (+ device query) or `KHR_platform_gbm`, and aborts in
`loadGLProc` on any NULL `eglGetProcAddress`. [`bringup/egl-mali-shim.c`](../bringup/egl-mali-shim.c)
(LD_PRELOAD):

- adds `EGL_EXT_device_{base,enumeration,query} EGL_EXT_platform_device EGL_KHR_platform_gbm
  EGL_MESA_platform_gbm` to the client extensions;
- `eglQueryDevicesEXT` returns one fake device whose `EGL_DRM_DEVICE_FILE_EXT` is `/dev/dri/card0` and
  `EGL_DRM_RENDER_NODE_FILE_EXT` is `/dev/dri/renderD128` (mediatek-drm);
- `eglGetPlatformDisplay(EXT)` for any platform returns the default display;
- stubs `eglDebugMessageControlKHR` (looked up unconditionally);
- inside the `Hyprland` process only, clears `LD_PRELOAD`/`LD_LIBRARY_PATH` so its children use Mesa
  (the uwsm python helper and `start-hyprland` in the launch chain must keep them).
- [`bringup/procs-check.c`](../bringup/procs-check.c) checks every proc Hyprland loads: all resolve.

Buffers: Aquamarine still allocates through Mesa's GBM with `GBM_ALWAYS_SOFTWARE=1` (kms_swrast → linear XR24
dumb buffers, `AQ_NO_MODIFIERS=1`, `HYPRLAND_EGL_NO_MODIFIERS=1`); libmali imports them as DMA-BUFs. Aquamarine's
own `CDRMRenderer` now also comes up on the Mali (it failed before, harmlessly).

## Wiring

  `EnvironmentFile=-/etc/quigon/gpu.env` — only the compositor unit gets the GPU; apps started through
  `uwsm app` get the user manager's environment.

## Vulkan: libmali is also a Vulkan 1.4 driver (later the same day)

- ChromeOS ships `/usr/share/vulkan/icd.d/mali_icd.json` → `libmali.so.0`: **Vulkan 1.4.313, Mali-G57, driver
  54.1.0, conformance 1.4.1.0**. The only WSI is `VK_EXT_headless_surface` (no Wayland).
- Features of note: geometry + tessellation shaders **true** (emulated), `multiDrawIndirect`, `shaderFloat64`,
  `shaderClipDistance/CullDistance`, `fillModeNonSolid`, `vertexPipelineStoresAndAtomics` **false**. Has
  `VK_EXT_external_memory_dma_buf`, `VK_EXT_image_drm_format_modifier`, `VK_KHR_external_{memory,semaphore,fence}_fd`,
  `VK_EXT_queue_family_foreign`, calibrated timestamps.
- **Wayland WSI**: ARM's [vulkan-wsi-layer](https://gitlab.freedesktop.org/mesa/vulkan-wsi-layer) built on the device
  ([`scripts/build-vulkan-wsi-layer.sh`](../scripts/build-vulkan-wsi-layer.sh)) with three fixes:
  1. It requires `zwp_linux_explicit_synchronization_v1`; Hyprland 0.56 has neither that nor `linux-drm-syncobj`
     here (only `zwp_linux_dmabuf_v1` v5 + `wp_presentation`). Without it the surface init fails, vkCreateWaylandSurfaceKHR
     returns an error vkcube ignores, and the next call segfaults in libmali with `surface=0x0`.
     [`vulkan-wsi-layer-quigon.patch`](../port/quigon/patches/vulkan-wsi-layer-quigon.patch)
     makes it optional and waits for the present fence on the CPU (`poll` on the sync fd) before `wl_surface_commit`.
  2. Default allocator heap `linux,cma` doesn't exist; use `-DWSIALLOC_MEMORY_HEAP_NAME=system`, and give
     `/dev/dma_heap/system` to the video group (udev rule; it is root 0600 by default).
  3. `-Werror` + GCC 16 false positive in `wsialloc_helpers.c` → strip `-Werror`.
  Install as an **implicit** layer (`/etc/vulkan/implicit_layer.d`), with the Mali ICD in `/etc/vulkan/icd.d`: as an
  explicit layer its `VK_KHR_wayland_surface` doesn't show up in the instance-extension query apps make first.
  Debug builds log with `VULKAN_WSI_DEBUG_LEVEL=3`; Release builds compile the log out.
- Result: `vkcube --wsi wayland` 600 frames in 10.1 s = **59 fps** (vsync), no kbase faults.
  **GTK 4.22 apps now pick `GskVulkanRenderer` on the Mali-G57 by themselves** (Nautilus checked).

## Ghostty on the GPU: blocked (parked)

Ghostty 1.3 needs desktop OpenGL 4.3. Mesa Zink on the Mali Vulkan driver gives **OpenGL 3.2 core** (ES 3.1).
With `MESA_LOADER_DRIVER_OVERRIDE=zink GALLIUM_DRIVER=zink MESA_GL_VERSION_OVERRIDE=4.3 MESA_GLSL_VERSION_OVERRIDE=430`
(and `LIBGL_ALWAYS_SOFTWARE` unset) Ghostty loads "OpenGL 4.3" but its shader link fails:
`Too many vertex shader storage blocks (1/0)`. Zink exposes 0 vertex SSBOs because
`vertexPipelineStoresAndAtomics = false`, although Vulkan allows read-only storage buffers there. Fix would be a Mesa
Zink patch (allow read-only vertex SSBOs) + rebuild; GTK also logged `ZINK: failed to dup dmabuf fd`. foot stays default.

## Chrome on the GPU: works, but slower here (not enabled)

`--use-angle=vulkan --enable-features=Vulkan,DefaultANGLEVulkan,VulkanFromANGLE --ozone-platform=wayland`:
GL_RENDERER `ANGLE (ARM, Vulkan 1.4.313 (Mali-G57 (0x90010010)), Mali-G57-54.1.0)`, Skia `GaneshVulkan`, GPU
compositing / rasterization / WebGL / WebGPU **enabled**. But Chrome logs `'--ozone-platform=wayland' is not compatible
with Vulkan`, and a 1600×900 2D canvas with 2,000 arcs/frame runs **32.8 fps on the GPU vs 41.2 fps** in the default
(llvmpipe, `gpu_compositing: disabled_software`) — the same pattern as the phone. Checked over CDP
(`SystemInfo.getInfo`, `Runtime.evaluate`) with Node's built-in WebSocket and throwaway `--user-data-dir`s.
Untried: ANGLE's GLES backend on libmali EGL (the Wayland-native path), and real workloads (scrolling, video, WebGL).

- Don't clean up with `pkill -f <name>` from an SSH command whose own text contains `<name>`; it kills the SSH session.

## Apps' OpenGL on the GPU: Zink (evening)

- Zink refused the Mali under Wayland: `ZINK: failed to choose pdev`. With a DRM device fd, `choose_pdev` →
  `zink_get_display_device` matches `VkPhysicalDeviceDrmPropertiesEXT.renderMajor/Minor` (from
  `vkGetPhysicalDeviceProperties2`) and never checks the extension, but the Mali ICD leaves the struct empty. The WSI
  layer patch now also hooks `vkGetPhysicalDeviceProperties2(KHR)` and fills it from `stat()` of
  `/dev/dri/renderD128` / `card0` (`QUIGON_VK_DRM_RENDER` / `QUIGON_VK_DRM_PRIMARY` override) when the driver didn't.
- glmark2-es2-wayland 1280×720 (build, texture, phong, desktop): **llvmpipe 59 → Zink on Mali 670**.
- Session: `quigon-omarchy` exports `MESA_LOADER_DRIVER_OVERRIDE=zink` for apps when `/etc/quigon/gpu.env` exists
  (else the old llvmpipe variables). The compositor unit's drop-in `UnsetEnvironment=MESA_LOADER_DRIVER_OVERRIDE`
  and `gpu.env` keeps `GBM_ALWAYS_SOFTWARE=1` for Aquamarine's scanout buffers. A `uwsm-app`-launched `eglinfo -p wayland`
  reports `zink Vulkan 1.4(Mali-G57 (ARM_PROPRIETARY))`, GL 3.2 core / ES 3.1.
- Zink can't allocate *exportable* images on the Mali (`vkCreateImage failed (VK_ERROR_INVALID_EXTERNAL_HANDLE)`), so
  anything that allocates through Mesa GBM with Zink (Chrome/Electron's GbmPixmapWayland:
  `Cannot create bo with format=RGBA_8888 and usage=Scanout|Rendering|Texturing`) falls back to software. Forcing
  `GBM_ALWAYS_SOFTWARE=1` for such an app also forces its EGL to llvmpipe.

## Chrome on the GPU: ANGLE GLES on libmali + minigbm (the ChromeOS stack)

| Chrome | GL_RENDERER | 2D canvas (2,000 arcs, 1600×900) |
|---|---|---|
| default | ANGLE (Mesa, llvmpipe) | 41 fps |
| `--use-angle=vulkan` | ANGLE (ARM, Vulkan 1.4.313 (Mali-G57)) | 33 fps (Wayland+Vulkan readback) |
| with Zink as Mesa driver | GPU disabled (GBM export failure) | 40 fps |
| **`--use-gl=angle --use-angle=gles` + chrome-lib** | **ANGLE (ARM, Mali-G57, OpenGL ES 3.2 v1.r54p1)** | **58.7 fps** (60 Hz cap) |

- ANGLE loads the system EGL with `dlopen("libEGL.so.1")` + `dlsym(handle, …)`, so the LD_PRELOAD shim is bypassed
  (`Failed to get system egl display`). [`scripts/build-chrome-lib.sh`](../scripts/build-chrome-lib.sh) builds the shim
  as `libEGL.so.1` with DT_NEEDED `libmali.so.0`; `dlsym` on its handle searches the shim first, then libmali. ANGLE asks
  for platform `0x31d7` (`EGL_PLATFORM_SURFACELESS_MESA`); the shim maps it to libmali's default display.
- Buffers: ChromeOS `libminigbm.so.1.0.0` (RELR-patched with the generalized
  [`scripts/patch-cros-relr.py`](../scripts/patch-cros-relr.py)) as `libgbm.so.1` picks its `mediatek` backend on
  `renderD128`. Harmless log: `[minigbm:mediatek_bo_create_with_modifiers(415)] no usable modifier found`.
- [`quigon-chrome`](../port/quigon/root/usr/local/bin/quigon-chrome) wraps `/usr/bin/google-chrome-stable` with that
  `LD_LIBRARY_PATH` and the flags when GPU mode is on; `~/.local/share/applications/google-chrome.desktop` (a copy with
  `Exec=/usr/local/bin/quigon-chrome`) makes Omarchy's browser launcher and webapps use it (they read `Exec=` from
  `~/.local/share/applications` first). Things Chrome itself spawns inherit the `LD_LIBRARY_PATH`.

## Ghostty on the GPU: patched private Zink Mesa (works)

[`scripts/build-mesa-zink.sh`](../scripts/build-mesa-zink.sh) builds Mesa 26.2.4 (same version as the system's) with
only Zink, Wayland, EGL, GBM, glvnd, no LLVM, into `/opt/quigon-gpu/mesa-zink` (~a few minutes on the device), with one
patch in `zink_screen.c`: when `QUIGON_ZINK_RO_VERTEX_SSBO=1`, don't zero `max_shader_buffers` for vertex/tess/geometry
stages just because `vertexPipelineStoresAndAtomics` is false (Vulkan allows read-only storage buffers there; Ghostty only
reads them). That fixes `Too many vertex shader storage blocks (1/0)`.

Then GTK 4.22 tried to pass the GL texture as a DMA-BUF, which Zink can't export on the Mali
(`couldn't allocate memory`, `Failed to download 3024x1820 dmabuf texture`). Ghostty overwrites `GDK_DISABLE` with
`gles-api,vulkan` at startup (`application.zig`), so [`bringup/ghostty-gpu-preload.c`](../bringup/ghostty-gpu-preload.c)
hooks `setenv` to append `dmabuf,offload`, and hooks `execve`/`execvpe` to strip `LD_PRELOAD`, `LD_LIBRARY_PATH`,
`__EGL_VENDOR_LIBRARY_FILENAMES`, `MESA_GL(SL)_VERSION_OVERRIDE`, `QUIGON_ZINK_RO_VERTEX_SSBO` from the shell's
environment (child env check: 0 leaks). Remaining harmless log lines: `zink: failed drmPrimeFDToHandle Invalid argument`,
`Unable to get a valid memory fd`, a GLib `g_close(fd:0)` warning.

[`quigon-ghostty`](../port/quigon/root/usr/local/bin/quigon-ghostty) sets it up (GL reported as 4.3);
`~/.local/share/applications/com.mitchellh.ghostty.desktop` points `Exec`/`TryExec` at it. Screenshot confirmed correct
rendering.

| Ghostty, `seq 1 2000000` | wall | user | sys |
|---|---|---|---|
| llvmpipe | 4.32 s | 18.11 s | 2.23 s |
| **patched Zink on Mali** | **2.26 s** | **3.06 s** | **1.65 s** |

## How much does Zink cost? Native libmali GLES vs Zink, same GPU

[`bringup/gles-bench.c`](../bringup/gles-bench.c): identical offscreen GLES 3 workload, 1920×1200 RGBA8 target, 60 frames
each after a warm-up pass, `glFinish` per frame. Native = libmali default display; Zink = Mesa surfaceless with
`MESA_LOADER_DRIVER_OVERRIDE=zink` on the libmali Vulkan driver.

| ms/frame | native libmali GLES | Zink → libmali Vulkan | Zink overhead | llvmpipe |
|---|---|---|---|---|
| 5,000 draw calls (per-draw uniforms) | 5.62 | 10.53 | ~1.9× | 24.73 |
| heavy fragment shader, 3 full passes | 101.91 | 103.59 | ~2% | 784.51 |
| full-screen texture upload + draw | 2.55 | 4.26 | ~1.7× | 17.39 |

GPU-bound work costs the same; per-call driver work and uploads cost ~2× on the CPU side.

## Every Electron app on the GPU automatically (2026-10-09)

- Electron apps launched normally inherit the session's Zink defaults. Chromium's `GbmPixmapWayland` can't allocate
  through Mesa GBM + Zink, so they silently fall back to software rendering (they work, just on the CPU).
- [`quigon-electron-sync`](../port/quigon/root/usr/local/bin/quigon-electron-sync) (root, pacman hook
  `zz-quigon-electron-sync.hook` on any `usr/share/applications/*.desktop` change, also re-run by quigon-doctor):
  - finds desktop entries whose program is a Chromium build: `resources.pak` + `v8_context_snapshot.bin`/`snapshot_blob.bin`
    next to the ELF, also through launcher scripts (absolute paths in the script, quoted ones with spaces) or system
    `electronNN`. Chrome-family browsers are skipped (quigon-chrome handles them).
  - writes `/usr/local/share/applications/<same name>.desktop` with `Exec=/usr/local/bin/quigon-electron …`. The session's
    `XDG_DATA_DIRS=/usr/local/share:/usr/share` makes it win over the packaged entry, with no per-user files.
  - for bare-command `Exec=` lines also writes a `/usr/local/bin/<cmd>` shim (PATH has /usr/local/bin before /usr/bin),
    so terminals, keybindings and `uwsm-app -- obsidian` get the GPU too.
  - generated files carry `# generated by quigon-electron-sync`; they're removed when the app is uninstalled. Anything
    without the marker is left alone.
  - `quigon-electron-sync --status` lists running Chromium GPU processes and whether each mapped `libmali`.
- `quigon-electron` now adds `--use-gl=angle --use-angle=gles` itself (after the program, or after `env VAR=… prog`) and
  is re-entrant (`QUIGON_ELECTRON=1`), so a shim inside an override doesn't double-wrap.
- Verified: Obsidian 1.14.4 (launched as `obsidian`, via the shim) and Slack 4.52.171 (Omarchy's aarch64 `slack-desktop`, via
  `gtk-launch slack`, the desktop path) both have GPU processes with `use-gl=angle` that map libmali. Grok Bot's earlier
  per-user `~/.local` override was removed in favor of the generated one. Grok Bot still needs its own hardware
  acceleration setting on; with it off, its GPU process shows `use-gl=disabled`.
- Discord has no arm64 Linux build. Omarchy's Discord entry is a web app (`omarchy-launch-webapp`). That runs the default
  browser's `Exec=` from `~/.local/share/applications/google-chrome.desktop`, i.e. quigon-chrome, so web apps are on
  the GPU already.
- To launch apps in the session from SSH on Hyprland's Lua config:
  `hyprctl dispatch 'hl.dsp.exec_cmd("uwsm-app -- obsidian")'` (the old `dispatch exec …` form is a Lua syntax error).

## GPU by default for desktop apps (Zink), with exceptions (2026-10-09)

- Apps launched from the desktop (keybinds, Omarchy menu, terminal) inherit **Hyprland's** environment, i.e. `gpu.env`,
  not the systemd user manager's (`systemctl --user set-environment` only reaches systemd/D-Bus-started things). Also:
  `uwsm-app` run from an SSH shell passes *that* shell's environment, which made several of my test launches misleading.
- `gpu.env` now carries `MESA_LOADER_DRIVER_OVERRIDE=zink` and `SDL_VIDEODRIVER=wayland,x11` for everything Hyprland
  starts (Hyprland itself renders through libmali; its GBM stays `GBM_ALWAYS_SOFTWARE=1`).
- **Exception, the Omarchy bar**: the real Omarchy shell crashes on Zink (`vkCreateImage … VK_ERROR_INVALID_EXTERNAL_HANDLE`,
  then a segfault in Mesa's Wayland `swapBuffers`), while a minimal Quickshell window runs fine on Zink in every variant
  tested — so it's something the bar does (likely DMA-BUF imports), not Qt Quick on Zink.
  [`fix-omarchy-launch-shell`](../port/quigon/root/usr/local/bin/fix-omarchy-launch-shell) runs its Quickshell on llvmpipe
  (pacman hook re-applies it).
- **SDL games / X11**: Cave Story (doukutsu-rs, SDL2) crashed on Zink only while `DISPLAY` was set — SDL picks X11, and
  Zink under Xwayland needs DRI3 image export; with DRI3 disabled GLX has no visual at all. `SDL_VIDEODRIVER=wayland,x11`
  fixes it (bisected with the full session environment). Other X11-only OpenGL apps: `quigon-nozink`.
- Session launcher also exports Zink + `QT_QUICK_BACKEND=software` + `SDL_VIDEODRIVER` for systemd-started apps.
- **Correction, same day:** the bar exception now uses `QT_QUICK_BACKEND=software` instead of stripping Zink from the
  bar's environment — apps launched from the Omarchy launcher/menus run *inside* the bar and inherited its llvmpipe
  settings (Cave Story ran at ~650% CPU on llvmpipe). With Qt Quick in software the bar never loads Mesa (0 libgallium
  maps) and its children keep Zink. Also found a stale `LIBGL_ALWAYS_SOFTWARE=1` in the user manager from the earlier
  crash fix (it outlives sessions and overrides `MESA_LOADER_DRIVER_OVERRIDE`): unset it, and the compositor drop-in now
  has `UnsetEnvironment=LIBGL_ALWAYS_SOFTWARE GALLIUM_DRIVER`. Takes effect for apps at the next session start.

## The Omarchy bar on the GPU: Qt Quick on libmali Vulkan (2026-10-09)

- Zink still can't run Qt Quick here (`vkCreateImage … VK_ERROR_INVALID_EXTERNAL_HANDLE`), but Qt Quick doesn't need
  OpenGL: `QSG_RHI_BACKEND=vulkan` (with `QT_QUICK_BACKEND` unset) makes its RHI talk Vulkan directly. On this machine
  that's ChromeOS's libmali Vulkan ICD plus the patched ARM WSI layer for `VK_KHR_wayland_surface`, the same path GTK 4
  apps use. No Mesa involved.
- Test bar: Qt picked `'Mali-G57' 54.1.0 (api 1.4.313)`, `VK_KHR_wayland_surface`, a 3-buffer FIFO swapchain at
  3072×80 (1.6× scale). It rendered and animated (`GraphicsInfo.api` = 5 = Vulkan). The process maps
  `libmali.so.0.54.1.relr` and `libVkLayer_window_system_integration.so`.
- The real Omarchy shell on Vulkan: no warnings beyond the usual portal app-ID one. Idle, 50 s window: software
  1 tick vs Vulkan 2 ticks (both ~0% CPU). PSS 203 MB → 215 MB. RSS looks like +350 MB, but that's the shared libmali
  mapping counted in full.
- [`bar-env`](../port/quigon/root/usr/local/libexec/quigon/bar-env) prints the bar's env(1) args on each launch:
  Vulkan by default; software when GPU mode is off, when `/etc/quigon/bar-software` exists, or after 5 launches within 60 s
  in one session. The crash-loop fallback notifies once and is remembered in `$XDG_RUNTIME_DIR` until the next login.
  Omarchy's launcher already relaunches the bar after a crash, so each relaunch goes through bar-env.
  `fix-omarchy-launch-shell` rewrites the launcher's `env QT_QUICK_BACKEND=software quickshell` to
  `env $(/usr/local/libexec/quigon/bar-env) quickshell` (it also upgrades the older variants). quigon-doctor checks the
  patch and reports whether the running bar maps libmali.
- Apps launched from the bar's own menus inherit `QSG_RHI_BACKEND=vulkan`. Qt Quick apps started there render on
  Vulkan too; the session default elsewhere is still `QT_QUICK_BACKEND=software`. If Vulkan holds up, the session
  default could switch to Vulkan for all Qt Quick apps.
- Still to watch: suspend/resume and lock/unlock with the bar on Vulkan (the lock screen is the same Quickshell
  process).
