# Mainline kernel + Panfrost: survey (2026-10-09)

Goal (README to-do "the real fix"): boot a mainline-based kernel on quigon, with Panfrost (open GPU driver)
instead of ChromeOS's kernel + libmali + shims. Sources are kept outside the repo in `~/src/quigon-kernel/`:
`linux-next` (next-20261008, shallow) and Google's `chromeos-6.6` (shallow), the kernel running on the device today.

## What exists

**Merged in linux-next** (`grep -rl mt8189 drivers`): IOMMU (`mtk_iommu.c`), SMI (`mtk-smi.c`), power domains
(`mtk-pm-domains.c`), pinctrl (`pinctrl-mt8189.c`), MMC (`mtk-sd.c`), JPEG, regulator coupler. Also bindings for
watchdog, I2C, eFuse, timer, pwrap, SPMI, ADC. **No `mt8189.dtsi` and no clock driver in linux-next yet.**

**Posted, not merged** (Patchwork project linux-mediatek, `q=mt8189`, 64 series):

| Area | Latest series |
|---|---|
| Clocks | Collabora "MT8189: Add support for system and base clock controllers" v6 [27] (2026-09-04); MediaTek "Add support for MT8189 clock controller" v6 [18] (2026-03-09) |
| Power controller | "Add support for MT8189 power controller" v1 [3] |
| Display | "Add MediaTek SoC DRM support for MT8189" v1 [13]; "drm/mediatek: Add DSC, WDMA, MT8189/96 DSI support" v9 [13] |
| Video codec | "Enable video decoder & encoder for MT8189" v10 [10] |
| DTS | "Add mt8189 dts evaluation board and Makefile" v7 [9] |
| Other | SCP v3, thermal LVTS v2/v3, cpufreq-hw bindings, audio (ASoC), MMC, PCIe gen3 + T-PHY + UART-DMA + scpsys bindings, stmmac, devapc, SMI, IOMMU |
| **GPU** | **nothing posted** |
| UFS, USB controller | not in the linux-mediatek list (check linux-scsi / linux-usb) |

**ChromeOS 6.6** has everything for the whole Skywalker family: `mt8189.dtsi`, `mt8189-skywalker.dtsi`,
**`mt8189-skywalker-obiwan.dts`** (`compatible = "google,obiwan", "mediatek,mt8189"`), and overlays for our variants
(`-rt5682s-rt1019p` audio, `-kb`, `-kb-backlight`, `-touchscreen`, `-panel-follower`). That's the reference for
porting missing pieces forward.

## GPU: close to existing Panfrost support

ChromeOS's node:

```
gpu: gpu@13000000 {
	compatible = "mediatek,mt8189-mali", "arm,mali-valhall-jm";
	reg = <0 0x13000000 0 0x4000>;
	interrupts = <GIC_SPI 271 …>, <GIC_SPI 270 …>, <GIC_SPI 269 …>;  /* job, mmu, gpu */
	operating-points-v2 = <&gpu_opp_table>;
	clocks = <&mfg_clk CLK_MFG_BG3D>;
	power-domains = <&scpsys MT8189_POWER_DOMAIN_MFG2>, <&scpsys MT8189_POWER_DOMAIN_MFG3>;
	power-domain-names = "core0", "core1";
	nvmem-cells = <&gpu_avs0>, <&gpu_avs1>, <&gpu_avs2>;   /* speed-bin / AVS fuses */
};
&gpu { mali-supply = <&mt6359_vproc1_buck_reg>; };   /* skywalker.dtsi; SRAM on ldo_sram_gpu */
```

There's no GPU microcontroller (GPUEB) like MT8196. Panfrost in linux-next already has `mediatek,mt8370-mali`
(Genio 510, also Mali-G57, also 2 power domains). So the Panfrost side is probably a new compatible reusing
`mediatek_mt8370_data` (+ the binding). The real dependencies are the MFG clock (clock series), the MFG2/MFG3
power domains (merged driver; check MT8189 MFG entries), the MT6359 PMIC regulators (pwrap/SPMI bindings
posted), and the DTS.

## Plan

0. **Build + safe test loop.** Cross-compile with clang (`make LLVM=1 ARCH=arm64`; no aarch64 gcc on the XPS), FIT
   image signed with the devkeys like today's kernel. Test slot = **KERN-B** (ChromeOS's spare A/B slot, 32 MiB;
   back it up first). Each test is `priority=4 tries=1 successful=0`: the firmware spends the single try, nothing
   marks it good, and the next boot falls back to KERN-C (Omarchy, priority 3). Self-contained initramfs (no storage
   drivers needed); `panic=5`, early watchdog, pstore/ramoops (ChromeOS reserves the region; read
   `/sys/fs/pstore` from Omarchy after the warm reboot). First, a dry run with the current ChromeOS kernel in
   KERN-B, to prove boot-once + fallback.
1. **Headless:** linux-next + clock series + a trimmed obiwan DTS (CPUs, GIC, timer, UART, pinctrl, clocks, power
   domains, watchdog, PMIC). Then storage (UFS/MMC), USB, PCIe → MT7921 Wi-Fi, SSH. Port what's missing from
   chromeos-6.6.
2. **Display:** mmsys/OVL/RDMA + eDP + backlight (DRM series), Hyprland on llvmpipe.
3. **GPU:** Panfrost compatible + opp/regulators + DTS node; Mesa's Panfrost (stock Arch) for GLES/GL, PanVK for
   Vulkan.
4. **The rest:** audio, suspend, thermal, cpufreq, keyboard backlight, video codec (V4L2 series).

Anything we write that works goes upstream.

## Stage 0 progress

- `vboot-utils` (alarm) gives `futility`; the devkeys (kernel.keyblock, kernel_data_key.vbprivk) are copied from
  ChromeOS's ROOT-A to `/usr/local/share/quigon/devkeys`.
- KERN-B (ChromeOS's original) is backed up to `/root/kern-backup/kern-b-chromeos.bin` and to the repo's ignored
  `private/kern-b-chromeos-20261009.bin` (sha256 07ecbe85…).
- **Boot-once dry run passed (2026-10-09):** the current kernel, repacked with `root=PARTUUID=<ROOT-C>` (the stock
  `%U/PARTNROFF=1` would point at ROOT-B from slot 4) plus `quigon.test=kernb`, written to KERN-B with priority 4,
  tries 1, successful 0. Reboot 1 booted it (marker in `/proc/cmdline`); the firmware then left KERN-B at priority 0,
  tries 0. Reboot 2 fell back to KERN-C. About 30 s each to SSH.
  [`scripts/test-kernel.sh`](../scripts/test-kernel.sh) (installed as `quigon-test-kernel`) does this:
  `--vmlinuz <FIT> <cmdline>` or `<oldblob> <cmdline>`, plus `--status`, `--disarm`, `--restore-chromeos`.
- **pstore works and is firmware-provided:** depthcharge adds a `reserved-memory/ramoops` node (0xffec5000, 1 MiB) to
  whatever DT it boots, so a mainline kernel with `CONFIG_PSTORE_RAM` gets it too. It already caught last night's
  crash: `BUG: Bad page map` in a Chrome process right after the mtk-vcodec-dec rebind, then
  `Kernel panic - not syncing: hung_task: blocked tasks` 3.5 min later. **No `panic=` on the normal command line,
  so it froze instead of rebooting.** Test kernels get `panic=5`.

## Stage 1 (2026-10-09)

Build host: a DGX Spark (GB10, 20 Arm cores, native arm64 gcc), ~1 min for a full trimmed
build, ~15 s incremental (the XPS 13 took 17 min for an untrimmed defconfig). Tree on the Spark:
`~/quigon-kernel/linux-next` = next-20261008 + Collabora's MT8189 clock series v6 (Patchwork series 1158200) + the
Genio 520/720-EVK series v3 (1172898, which brings a mainline `mt8189.dtsi`), with our `mt8189-quigon.dts` and
ChromeOS's `mt8189-pinfunc.h` (mainline's pinmux header isn't merged).

- [`scripts/mainline-config.sh`](../scripts/mainline-config.sh): defconfig trimmed to MediaTek (no other ARCH_*, no
  DRM/sound/media/ACPI/EFI/ATA/MTD/ftrace…), MT8189 clocks/pinctrl/power domains/watchdog/PCIe/MT7921E built in,
  pstore console, xz-embedded initramfs. Image ~30 MB: depthcharge decompresses into a fixed buffer, and ChromeOS's
  own kernel is 33 MB uncompressed, so stay under that.
- [`scripts/mainline-pack.sh`](../scripts/mainline-pack.sh): FIT (lz4 Image + DTB, config compatible
  `google,obiwan-rev3-sku196620`, `-sku196620`, `google,obiwan`; this machine is SKU 196620 = 0x3000c, board rev 3)
  → `quigon-test-kernel`. [`scripts/mainline-cycle.sh`](../scripts/mainline-cycle.sh) runs a whole round (sync to
  the Spark, build, pack, arm, reboot, wait, `mainline-log`).
- [`port/quigon/mainline/init-stage1.sh`](../port/quigon/mainline/init-stage1.sh): the initramfs `/init`, which logs
  `QM:` lines and keeps the watchdog fed.

**s1a: first boot of a mainline kernel on quigon worked.** 7.3.0-rc6-next-20261008 reached `/init`, 8 CPUs, 7.7 GiB.
All MT8189 clock controllers, pinctrl, mtk-power-controller (14 domains), mtk-wdt, mt6577-uart, efuse and ramoops
bound, with nothing deferred. Then it rebooted and fell back to Omarchy as designed (~65 s round trip, including the
dev-screen wait). Only failure: `mt-pmic-pwrap … failed with error -22` = "slave pmic should be defined in dts"
→ include `mt6359.dtsi` with ChromeOS's PMIC interrupt (`&pio 194`).

Next (s1b/s1c): PMIC regulators, PCIe + MT7921 Wi-Fi (pins from ChromeOS: WAKEN/PERSTN/CLKREQN on GPIO48-50, Wi-Fi
kill GPIO146 high), and an initramfs with wpa_supplicant + dropbear, so a test boot joins Wi-Fi and stays up for
SSH. Credentials and the SSH key exist only in the build host's initramfs tree.

Practicalities: closing the lid suspends the Chromebook even on AC, which stops remote testing (proposed:
`HandleLidSwitchExternalPower=ignore`). Every unattended test boot waits ~30 s at the developer screen and then beeps
(fixable only with the GBB `DEV_SCREEN_SHORT_DELAY` flag, which needs firmware write protection off).

### Later stage-1 rounds (2026-10-09)

- **s1b/s1d:** `mt6359.dtsi` + `&pmic { interrupts-extended = <&pio 194 IRQ_TYPE_LEVEL_HIGH>; }` → mt-pmic-pwrap and
  mt6397 bind, **46 MT6359 regulators** registered (`regulator_ignore_unused` on the command line).
- **s1c/s1e/s1g (PCIe + Wi-Fi on): the kernel hangs** (never back on the network, black screen, needs a power-button
  press; the cold power-off loses pstore). s1d (same but PCIe disabled, `mt8189-quigon-nopcie.dts`) boots fine, so the
  hang is the PCIe controller/PHY bring-up. The card is an MT7922 (14c3:0616, firmware `WIFI_MT7922_*`), not an MT7961.
- **Watchdog:** [`mainline-mtk-wdt-arm-at-boot.patch`](../port/quigon/patches/mainline-mtk-wdt-arm-at-boot.patch)
  (mtk_wdt registered at subsys_initcall, `mtk_wdt.start_timeout=31` arms it at probe, 0.022 s into boot). s1f
  self-test (init kills the feeder, PCIe off): **the reset works and pstore survives it.** But during a PCIe stall the
  kernel's own watchdog pinger keeps running on the other CPUs, so nothing resets. Next round (s1h) adds
  `watchdog.open_timeout=20` (the core stops feeding if userspace hasn't opened /dev/watchdog within 20 s) and
  `initcall_debug`, so a stall resets after ~50 s and pstore names the initcall that stalled.
- The test init asks DHCP for .22 (`udhcpc -r`); the round script scans the /24 for a test kernel that got another
  address.
- **s1h (open_timeout + initcall_debug), s1i (T-PHY v2 like ChromeOS), s1j (PCIe controller as a module, insmod'ed by
  /init under a 15 s timeout that then stops feeding the watchdog): all froze the same way.** Black screen; no watchdog
  recovery even though the s1f self-test proved the reset works. So the PCIe bring-up freezes the whole SoC (every
  CPU; even /init's fallback never ran), and the watchdog reset either doesn't take or the firmware stays wedged after
  it. Every attempt costs a power-button press and loses pstore. **Parked until the SuzyQ** (user ordered the parts):
  its AP UART shows the last line before the freeze, and it can reset the AP remotely. Candidates once it's
  visible: MAC register access with the PCIE power domain/clocks not really up (bus hang), T-PHY layout (v2/v3), the
  32 kHz `tl_32k` clock the Genio node adds (ChromeOS lists 5 clocks without it), missing resets.
- Next without PCIe (keep `mt8189-quigon-nopcie`): display (DRM series "Add MediaTek SoC DRM support for MT8189" v1,
  Patchwork 1013411; ChromeOS drives the internal eDP panel via `&edp_tx` + `edp-panel` with `pp3300_edp_x`), then
  Panfrost, USB, UFS.

## Stage 3: GPU, Panfrost (2026-10-09)

**s3b: Panfrost drives the Mali-G57 on mainline.**

```
panfrost 13000000.gpu: clock rate = 390000000
panfrost 13000000.gpu: mali-g57 id 0x9093 major 0x0 minor 0x1 status 0x0
panfrost 13000000.gpu: features: 00000000,000019f7, issues: 00000001,80000400
panfrost 13000000.gpu: Features: L2:0x08120206 Shader:0x00000000 Tiler:0x00000809 Mem:0x1 MMU:0x00002830 AS:0xff JS:0x7
panfrost 13000000.gpu: shader_present=0x5 l2_present=0x1
[drm] Initialized panfrost 1.6.0 for 13000000.gpu on minor 0
```

/dev/dri/card0 + renderD128, devfreq 390-560 MHz (idles at 390), MFG2/MFG3 runtime-suspended when idle, vproc1 675 mV,
vsram_proc1 750 mV.

What it took ([`mainline-mt8189-gpu.patch`](../port/quigon/patches/mainline-mt8189-gpu.patch) + DTS):
- `clk-mt8189-mfg.c`: the BG3D gate in mfgcfg (0x13fbf000), parent `mfg_sel_mfgpll`, modelled on clk-mt8188-mfg.c
  (Collabora's series leaves the multimedia/GPU clocks for later), with `need_runtime_pm`. Without runtime PM, reading
  the gate state (e.g. clk_summary) with the MFG domain off is an **SError panic** (s3a). The DT node gets
  `power-domains = <&spm MT8189_POWER_DOMAIN_MFG1>`. Plus `CLK_MFG_BG3D` in the dt-bindings header.
- Panfrost: `mediatek,mt8189-mali` → `mediatek_mt8370_data` (Mali-G57, 2 power domains core0/core1, "mali" supply).
- DTS: MFG0 > MFG1 > MFG2/MFG3 under `&spm` (absent from the Genio mt8189.dtsi), with `domain-supply` vproc1 (MFG0) and
  vsram_proc1 (MFG1), MFG1 clocks MFGPLL + MFG_REF_SEL, `mediatek,infracfg`. GPU node from ChromeOS. OPPs capped
  at the lowest six (390-560 MHz).
- **No regulator coupling:** ChromeOS couples vproc1/vsram_proc1, but mainline's mtk-regulator-coupler returns
  -ENOTSUPP for these, and that fails the *whole* MT6359 regulator probe (s3a: only regulator-dummy left, power
  controller and GPU deferred). Without it, SRAM (>= 750 mV) stays above core (<= 693.75 mV) anyway.

Next: render with Mesa's Panfrost. Mesa doesn't fit in the embedded initramfs (33 MB image limit), so bring up UFS
and use Omarchy's own Mesa from ROOT-C mounted read-only.

### UFS + Mesa on Panfrost (s3c-s3f)

- **UFS works on mainline** with ChromeOS's node translated: `mediatek,mt8183-ufshci` (mainline ufs-mediatek), clocks
  from topckgen + the Genio series' ufscfg-ao/-pdn controllers (unlabelled, so `&{/soc/clock-controller@112b8000}`
  path refs), resets unipro/crypto/hci (pdn) + mphy (ao), `mediatek,ufs-disable-mcq`, `-rtff-mtcmos`, `-broken-vcc`.
  All 14 partitions appear. The test init mounts ROOT-C **`-o ro,noload`** (no journal replay, so the real install
  is never written) and chroots into it.
- **Mesa (Omarchy's stock 26.2.4) on Panfrost:** `eglinfo -p surfaceless` → `OpenGL core profile renderer: Mali-G57
  MC2 (Panfrost)`.
- `bringup/gles-bench.c` (built into Omarchy as /usr/local/bin/gles-bench), offscreen 1920x1200:

  | | libmali (today's setup) | Panfrost, OPPs ≤560 MHz, no cpufreq (s3d) | Panfrost, full OPPs + cpufreq (s3f) |
  |---|---|---|---|
  | 5000 draws/frame | 5.72 ms | 27.58 ms | 21.68 ms |
  | heavy shader, 3 passes | 102.04 ms | 299.02 ms | **106.24 ms** |
  | texture upload + draw | 3.39 ms | 2.71 ms | **3.12 ms** |

  The draw-call gap is CPU time in the driver (the shader cache is off on the read-only root, and Panfrost's per-draw
  path is heavier).
- **cpufreq:** `mediatek,cpufreq-hw` (already in the Genio dtsi) needs `ARM_MEDIATEK_CPUFREQ_HW=y`; with it,
  policy0 0-5 (A55) goes to 2.0 GHz and policy6 6-7 (A78) to 2.6 GHz, schedutil.
- **GPU rails:** coupling attached once renamed to buck_vgpu/ldo_sram_gpu, but then MFG1 fails to power on (-EPERM)
  and the whole power controller probe fails (s3e, llvmpipe). Final: no coupling, `ldo_sram_gpu` fixed at 900 mV
  (>= core at every OPP), full ChromeOS OPP table 390-1100 MHz (s3f: devfreq has all 20 OPPs).

## Stage 4: internal display (s6a-s6d)

Display output on mainline: fbcon on the internal 1920x1200 panel (AUO B140UAX01.2). The pieces, all in
[`mainline-mt8189-display.patch`](../port/quigon/patches/mainline-mt8189-display.patch), which goes on top of the
watchdog and GPU patches:

- **Clocks:** `clk-mt8189-mmsys.c`: the MMSYS gates (child of the mmsys node, like mt8188 vdo0) and the MMINFRA
  gates, from ChromeOS's gate tables.
- **DRM:** MediaTek's MT8189 DRM series (Patchwork 1013411, v1, patches 11-13), hand-merged. Plus what it depends
  on from the MT8196 DVO series: `DDP_COMPONENT_DVO0/1`, `MTK_DISP_VIRTUAL` for the mmsys crossbar stages
  (`COMP0_OUT_CB4`), mmsys default-config tables, and mutex fixes.
  - The main path is OVL0 → RDMA0 → CB4 (crossbar) → DVO0, with no colour blocks.
  - The series' `conn_routes` (DVO1/DSI0) had to go. Mainline applies conn_routes to the *main* CRTC, and with no
    DVO1/DSI0 present the main path got an empty last slot: a NULL dereference in `mtk_crtc_atomic_enable` (s6b).
- **DVO:** `mtk_dvo.c`, ChromeOS's eDP-side video output block, ported to linux-next's bridge API.
- **eDP:** ChromeOS's `edp_ver` code paths for the newer eDP TX (MT8189/MT8196) in `mtk_dp.c`, plus a small
  `phy-mtk-edp.c`.
  - The panel is found over the AUX bus (`edp-panel`).
  - The link trains at the defaults: `max-linkrate-mhz = 5400`, 4 lanes, obiwan `swing-level = <3>`.
- **No IOMMU yet.** Mainline's `mtk_iommu` waits for every SMI larb it lists, and most of them have no clock driver
  here. The display ports stay in physical mode and buffers come from CMA (`cma=256M` on the test cmdline).
- **Display power domains:** MM_INFRA > DISP and EDP_TX_DORMANT, each with only its topckgen clock. The
  bus-protection subsys clocks come from controllers that live inside these domains, and referencing them would
  defer the whole power controller.

**Debugging aid: the hang-proof disk log.** A hard freeze plus the power-button reset wipes pstore. So the test
init writes its step name and the kernel log into a preallocated file on Omarchy's root,
`/var/lib/quigon/mainline-blklog`:

- The file is a single 4 MiB extent. Its block offset is passed as `quigon.blklog=` and the init writes the raw
  blocks with `dd conv=fsync`; the filesystem is never mounted read-write.
- The init writes only over zeros or its own `QBLK` header.
- `mainline-log` prints the disk log and clears it.

With the display drivers as modules (`DISP_MODULES=1`, `MODS=...`) and loaded one at a time, this showed that the
"hang" in s6a/s6b was an oops in the first modeset, not a bus freeze.

Next: boot the whole Omarchy userland on mainline. It still needs USB, audio, thermal, and Wi-Fi (PCIe freezes the
SoC, see stage 1).

## Stage 6: USB, Wi-Fi, PCIe (s7a-s8b)

- **USB:** [`mt8189-quigon-usb.dtsi`](../port/quigon/mainline/mt8189-quigon-usb.dtsi) adds XHCI3 (T-PHY port 3; the
  RTS5411 hub behind the external ports) and XHCI4 (XS-PHY; the MT7922's Bluetooth). The USB-A ports need VBUS from
  `pp5000_usb` (GPIO 131); without it nothing on them enumerates.
- **Wi-Fi through a USB dongle:** a TP-Link AC600 (RTL8821AU, rtw88) gives the test kernel a network.
  - Wi-Fi comes up early in the test init, so SSH works while the risky steps run.
  - Two init bugs had kept the network down since stage 1: Alpine's wpa_supplicant has no `-f`, and the
    initramfs files weren't mapped to root (`INITRAMFS_ROOT_UID` is the *build user's* uid, so dropbear refused
    `/root/.ssh`).
- **PCIe works.** The gen3 driver with numbered steps
  ([`mainline-pcie-gen3-qstep-debug.patch`](../port/quigon/patches/mainline-pcie-gen3-qstep-debug.patch)) loaded by
  hand on a live system powered the domain, linked up and enumerated the MT7922 (14c3:0616). It works with the
  pauses off as well (`qdelay=0`).
  - mt7921e associates at 130 Mbit/s on 2.4 GHz.
  - The stage-1 freezes didn't come back. What changed since: the controller is a module loaded after boot rather
    than built in, and the board now has display/USB/power-domain nodes. Built-in probing at boot is still to be
    retried.
- `qblk` (in the test initramfs) is the disk logger as a command, with `-bg` for once a second;
  [`bringup/devmem.c`](../bringup/devmem.c) is a static mmap devmem (plain `read()` on /dev/mem fails for MMIO).

## Stage 7: Omarchy on mainline (f1a-f1b)

`FULL=1 DTB=mt8189-quigon-all scripts/mainline-pack.sh <dir> <tag>` boots the real install on ROOT-C with the
mainline kernel, once; the next reboot is back on the ChromeOS kernel. The modules go into
`/usr/lib/modules/<release>` beside the ChromeOS kernel's.

Result: **the Omarchy desktop runs on mainline Linux + Panfrost + stock Mesa**. Hyprland drives the panel through
mediatek-drm at 1920x1200@60 and renders on the Mali with Panfrost (GLES 3.0 context). Chrome plays 1080p30 AV1 with
4 of 1086 frames dropped (software decode). There is no libmali, no shim and no ChromeOS kernel.

What it took on the Omarchy side (all inert under the ChromeOS kernel):

- `quigon-mainline.service` (ConditionKernelVersion `*-quigon*`): masks `/etc/quigon/gpu.env` (bind-mounts
  /dev/null over it), so every libmali/Zink wrapper falls back to stock Mesa, which is Panfrost here.
- `quigon-mainline-generator`: mainline has VTs, so logind wants the session on one. It gives `quigon-desktop@`
  tty1 (`TTYPath`, `XDG_VTNR=1`) and masks `getty@tty1`.
- `quigon-omarchy`: on mainline, `AQ_DRM_DEVICES` is the mediatek-drm card found by path (Panfrost takes card0), and
  no software overrides.
- `quigon-ghostty`: llvmpipe on mainline (see the to-do list).
- Cmdline `systemd.gpt_auto=0`. Otherwise systemd automounts the EFI partition (sda12), the FAT mount fails (512 B
  sectors on a 4 KiB-sector disk), and dbus-broker's namespace setup fails on `/boot`, taking NetworkManager and
  the desktop with it.
- Kernel config:
  - netfilter including the legacy iptables tables (ufw uses iptables-legacy), `uinput` (palm filter), zram zstd,
    Landlock (pacman's download sandbox).
  - `RTC_DRV_MT6397` **off**. Mainline's MT6359 RTC driver reads the year 60 years ahead (2086). systemd saved that
    as the last known time, and the next ChromeOS-kernel boot restored it. Fixed by setting the clock and touching
    the 96 future-dated files.
- Two side effects on the ChromeOS-kernel setup, both repaired:
  - **ufw was left `ENABLED=no`** after the first mainline boot's ufw start failed (no iptables modules yet).
    Re-enabled with an auto-revert armed.
  - The GPU boot guard disabled `gpu.env` after short ChromeOS-kernel boots that were cut off by test reboots.
    Restored and strikes reset.

## Stage 8: completing the desktop (f1c-f1o)

Each round: `QUIGON_BUILD_HOST=... scripts/mainline-full.sh <tag> [cmdline]` (installs the modules into Omarchy,
arms the boot-once slot, reboots, waits). `panic=10` sends a crashed mainline boot back to the ChromeOS kernel by
itself, and pstore keeps the log (`/sys/fs/pstore/console-ramoops-0`, `dmesg-ramoops-0`).

Working now:

### Video decode (works)

**H.264 and VP9 decode in hardware, bit-exact** (`quigon-test-video-decode`: 240/240 frames each; 1080p frames take
2-3 ms), and **Chrome uses it** (`quigon-chrome` passes the VA-API flags on both kernels; 1080p60 VP9 in Chrome: ~54
decoder interrupts a second, `libva-v4l2request` loaded in the GPU process).

[`mt8189-quigon-vcodec.dtsi`](../port/quigon/mainline/mt8189-quigon-vcodec.dtsi),
[`mainline-mt8189-vcodec.patch`](../port/quigon/patches/mainline-mt8189-vcodec.patch) +
[`-wip`](../port/quigon/patches/mainline-mt8189-vcodec-wip.patch) +
[`mainline-mt8189-vdec-gce-fixes.patch`](../port/quigon/patches/mainline-mt8189-vdec-gce-fixes.patch) +
[`mainline-mt8189-vdec-working.patch`](../port/quigon/patches/mainline-mt8189-vdec-working.patch).

What it took (each a difference from ChromeOS, found by diffing register snapshots, ChromeOS's live DT and
`chromeos-6.6` source, the shared VSI in SCP DRAM at 0x50034000, and the SCP firmware itself, an unstripped RISC-V ELF):

1. **Clock/genpd deadlock**: the vdec gate provider had runtime PM inside VDE0; now a plain provider (as ChromeOS),
   gates `CLK_IGNORE_UNUSED`.
2. **DEC_INIT is 24 bytes** (`shared_iova`) in the current firmware ABI; the firmware's log line showed 16.
3. **GCE**: nodes + mt8189 in mtk-cmdq-mailbox (DDR_EN, slot cycles), as ChromeOS initializes them. (Not the blocker
   in the end: no GCE thread runs during decode.)
4. **H.264 VSI layout**: `vdec_h264_slice_info_ext.reserved` sits at the end in the firmware ABI; mainline had it in
   the middle, so every slice parameter landed 8 bytes early. After this, frame 0 decoded bit-exact (3.3 ms).
5. **larb4 gate as VDE0 subsys clock** (`vdec-0`, as ChromeOS): without it only the first decode after a fresh VDE0
   power-up worked (frame 1 hung in the firmware's slice parse, even for all-I streams, and keeping VDE0 or the GCE
   clocks on from boot broke frame 0 too). With it: every frame.
6. 36-bit DMA mask on the decoder (as ChromeOS); buffers land in IOMMU region 1 (4-8 GiB).

**4K60 on YouTube** (Chrome, "2020 LG OLED | The Black 4K HDR 60fps", VP9 3840x2160@60): smooth, hardware-decoded,
and the MM21 detile **on the GPU**: 59.9 fps, 0 dropped/s, 63 decoder frames/s; Chrome's GPU process ~42% CPU
(renderer ~57% is YouTube's page, network ~22% the 30 Mbit/s stream).

ChromeOS has no MDP3 for MT8189 (its mdp3 driver only knows MT8183; scp.img has no MDP code), so it detiles the
decoder's MM21 output on the GPU. The VA-API driver now does the same
([`libva-v4l2-request-mtk-mm21.patch`](../port/quigon/patches/libva-v4l2-request-mtk-mm21.patch), `convert_gl.c`):
the CAPTURE planes are imported as linear RGBA8 EGLImages, a fragment shader gathers 4 bytes per texel into the
NV12 surface's planes (render targets), `glFinish` before the surface is handed on. Private EGL (`dlopen`
RTLD_LOCAL + eglGetProcAddress, surfaceless Mesa display, own GLES 3 context made current only for the draw), so it
coexists with Chrome's ANGLE. Only when Panfrost is loaded; else (and with `V4L2R_GL_DETILE=0`) the CPU path.

Per 4K frame: CPU 1 thread 8.5 ms, CPU 4 threads ~4 ms, GPU 2.9 ms (CPU idle). The first shader took 12.6 ms
regardless of GPU clock: Mali has no integer divider and the address math had six div/mod per fragment (a
fetch-only or write-only shader took ~2.5 ms); with shifts for the tile sizes and a float reciprocal for the one
division by the stride, 2.9 ms. Bit-exact: H.264/VP9 1080p 240/240, VP9 4K 120/120.

The occasional "1 of 240 frames differ" in `quigon-test-video-decode` is a missing *last* frame (239 delivered: an
end-of-stream drain race in the VA-API driver or ffmpeg), not a wrong one; every decoded frame matches. After a hang
(no longer expected) only a reboot resets the decoder.

Measuring decoder throughput: sum the IRQ count over all CPUs in /proc/interrupts (hwirq 520) and sleep explicitly;
`top -n1 -dN` returns at once (the delay only applies between iterations), which once made hardware decode look like
a software fallback.

Also found on the way: the LVTS thermal driver could read a stale sample (left by the ChromeOS kernel's driver across a
warm reboot) as critical right after initializing a controller itself, and power the machine off 0.09 s into boot.
It now ignores readings for 200 ms after that init.

### Video encode (works, 2026-10-10)

**H.264 encode in hardware**: `/dev/video*` "MT8189 video encoder" (stateful V4L2 M2M, NM12/NM21/YM12/YM21 in,
H.264 out up to 100 Mbit/s), usable through ffmpeg `-c:v h264_v4l2m2m` and GStreamer `v4l2h264enc`. 720p30 test
pattern at 4 Mbit/s: 60 frames in about a second of wall time, valid High-profile H.264.

[`mt8189-quigon-venc.dtsi`](../port/quigon/mainline/mt8189-quigon-venc.dtsi),
[`mainline-mt8189-venc.patch`](../port/quigon/patches/mainline-mt8189-venc.patch):
- MT8189 talks to the SCP's encoder service through MediaTek's "common firmware interface" (ChromeOS
  `uses_comm`; upstream it is part of the MT8196 encoder series): a 4 KB VSI in SCP memory carries the
  configuration, the working-buffer list and the frame/bitstream addresses, and the init message pair gains the
  codec type (in) and the VSI address (out). Ported ChromeOS's `venc_common_if.c` backend minus its VCP path and
  MMDVFS. The SCP firmware (`scp.img`, `middleware/venc/platform/mt8189`) has the matching layouts.
- DT: VEN0 under MM_INFRA with the larb7 gate as its subsys clock, the VEN1 clock controller, SMI larb7 (IOMMU
  region 1, so a 34-bit DMA mask), the encoder node. All from ChromeOS's mt8189.dtsi.
- The VEN1 clock provider had runtime PM; in the noirq resume phase genpd's power-on of VEN0 then failed to
  prepare the larb gate (-EACCES) and genpd marked the domain on anyway (it ignores errors there), so every resume
  ended in "already disabled" clock warnings. Now a plain provider like vdec_core (and ChromeOS).
- Output is byte-identical to the ChromeOS kernel's for the same input (same firmware). Known quirks there too:
  the coded height is padded to 32 (720p comes out as 1280x736, no cropping in the SPS), and on a synthetic
  moving pattern P-frames are small and lag (the encoder skips a lot); flat-frame tests map every frame correctly.
- Who uses it: ffmpeg/GStreamer/wf-recorder with a V4L2 M2M encoder. Not Chrome (on Linux it encodes through
  VA-API; V4L2 encode is only built for ChromeOS) and not Omarchy's screen recorder (gpu-screen-recorder).

### Suspend (works, 2026-10-10)

Mainline now suspends and resumes like the ChromeOS kernel: real SoC sleep, woken by the RTC (lid/keyboard/power
button through the EC's wake interrupt, untested remotely), the display coming back by itself, through
`systemctl suspend` / logind. [`mainline-mt8189-suspend.patch`](../port/quigon/patches/mainline-mt8189-suspend.patch),
[`mt8189-quigon-suspend.dtsi`](../port/quigon/mainline/mt8189-quigon-suspend.dtsi). What it took:

- **A real sleep state.** The firmware has no PSCI SYSTEM_SUSPEND; ChromeOS's DT has a `cpu-s2idle` idle state
  (PSCI CPU_SUSPEND `0x20180ff`, infinite min-residency so only s2idle uses it). When the last CPU enters it, TF-A and
  the SPM put the SoC to sleep. Mainline's mt8189.dtsi lacked it: s2idle had only ever been a shallow idle, which is
  why the RTC didn't wake it and the EC timed the sleep out.
- **DISP power domain always on.** At runtime it never powers off (MMSYS, the mutex, the DVOs have no runtime PM);
  in system suspend genpd tried, the power-off failed part way (genpd debugfs: "Rejected 1") and left the display's
  memory path blocked: after resume OVL stalled (no vblanks, larb0 stuck "busy") or the display faulted (SError,
  ~190 ms after video unmute, reported wherever the CPU happened to be: xhci, cpufreq, NetworkManager...).
- **MFG1 bus protection regmap.** MFG1's EMI GALS sleep-protect step needs the EMI config (`emicfg_ao_mem`,
  0x10270000) as the power controller's "SMI" regmap; without `mediatek,smi` the legacy lookup used index 0 and the
  step wrote INFRACFG_AO+0x84/0x88 instead. (`access-controllers` would be the modern way, but fw_devlink then waits
  ~10 s at boot for a driver the syscon never gets and the display probes before the IOMMU.)
- **PCIe kept up in s2idle**, as ChromeOS does (the bridge stays in D0; nothing restores its config space).
- **xhci-mtk:** IP0's one USB3 port is masked (its lanes carry DP) but stays powered from reset and the IP never
  reports sleep: power it down too; ChromeOS's retries and its MT8189 wakeup variant (`SSUSB_UWK_V1_10`); never gate
  the clocks of an IP that didn't sleep.
- **eDP TX v2:** suspend leaves the port as a runtime display-off does (powering it further down left AUX timing
  out and the display stalled); its `edp-tx-dormant` domain does power off, so resume checks `TOP_MEM_PD` (set by the
  boot-time AUX detection, 0 after a reset) and redoes the boot-time setup (PHY, port, power) when it was reset.
- **Watchdog:** `mtk_wdt.start_timeout` arms it at boot with only the kernel feeding it; its suspend stopped it only
  when userspace had it open, so it reset the SoC ~30 s into any longer sleep
  ([`mainline-mtk-wdt-stop-in-sleep.patch`](../port/quigon/patches/mainline-mtk-wdt-stop-in-sleep.patch)). def7 also stopped the
  core's ping worker over the sleep (`watchdog_stop_ping_on_suspend()`, upstream v2, after the Sashiko AI review of
  v1); dropped again for the next default (upstream v3): it stops the pings before tasks are frozen, so a short
  timeout could reset the system during the freeze, while the post-resume ping it avoided is harmless.
- **Power:** a 10-minute sleep used 20 mWh of the battery (the gauge's resolution, including the ~30 s awake with the
  panel on around it): well under 0.1 W asleep, i.e. weeks of standby.
- The `system-sleep/quigon-mainline-display` DPMS hook is gone: its 30 s `flip_done` stall was the DISP problem, and
  systemd now freezes `user.slice` (Hyprland) before running sleep hooks, so `hyprctl` from a hook only timed out.

How it was found (useful again): `pm_test=devices` vs `platform` to split normal callbacks from late/noirq ones; a
temporary PM-core switch that skipped the late/noirq callbacks of devices by name for bisecting; genpd's debugfs
`idle_states` (Usage *and* Rejected); register dumps of OVL/larb/SMI before and after; the watchdog
(`mtk_wdt.keep_in_suspend=1`) + pstore for hangs. `rmmod pcie_mediatek_gen3` freezes the SoC hard (no watchdog):
don't.

### Lid

A lid close never locked, under either kernel. Two causes:

1. Omarchy reads the lid from `/proc/acpi/button/lid`, which ARM doesn't have. The EC reports the lid as `SW_LID`
   on `cros_ec_buttons`, and [`omarchy-hw-laptop-closed`](../port/quigon/root/usr/local/bin/omarchy-hw-laptop-closed)
   in `/usr/local/bin` reads it with `evtest --query` and shadows Omarchy's.
2. Omarchy runs its lid actions from Hyprland bindings (`switch:on:Lid Switch`), and under Hyprland 0.56's Lua
   config no switch binding fires here. A binding on `cros_ec_buttons` didn't fire either, and neither did a uinput
   device named exactly "Lid Switch", although libinput sees the toggles (it suspends the touchpad).
   [`quigon-lid-watch`](../port/quigon/root/usr/local/libexec/quigon/quigon-lid-watch) reads `SW_LID` with
   python-evdev and runs the same commands. It is started from `~/.config/hypr/autostart.lua`
   ([`hypr-autostart-quigon.lua`](../port/quigon/user/hypr-autostart-quigon.lua)).

The wrappers [`omarchy-system-lid-close`](../port/quigon/root/usr/local/bin/omarchy-system-lid-close) and
[`omarchy-hyprland-monitor-clamshell`](../port/quigon/root/usr/local/bin/omarchy-hyprland-monitor-clamshell) also
switch the panel off on close and back on on open. Verified on mainline: close locks and the panel goes off
(DPMS), open brings it back on the lock screen. On mainline that is what keeps a closed laptop dark (it doesn't
sleep, and it is fanless); under ChromeOS's kernel it adds the lock before suspend on battery, and lock + panel off
on the charger.

### External displays (2026-10-10)

Both external outputs hang off the second display pipe (OVL1 -> RDMA1 -> mmsys crossbar), which mediatek-drm routes
to whichever connector is in use (connector routes on the external CRTC, `{1, DVO1}`, `{1, DSI0}`):
- HDMI: DSI0 (4 lanes) -> ITE IT61620 DSI-to-HDMI bridge on I2C6 0x58 -> HDMI type A (HPD on GPIO 139).
  [`mt8189-quigon-hdmi.dtsi`](../port/quigon/mainline/mt8189-quigon-hdmi.dtsi),
  [`mainline-mt8189-hdmi.patch`](../port/quigon/patches/mainline-mt8189-hdmi.patch): ChromeOS's `ite-it61620.c`
  and `phy-mtk-mipi-dsi-mt8189.c` ported to the 7.3 bridge API, mt8189 DSI data (2.5 Gbps/lane, PHY LP-00 while
  off, skywalker's HS-zero +6). The bridge powers up (1.0 V GPIO rail, VIO28 at 3.3 V as on ChromeOS, VCAMIO 1.8 V)
  and its chip ID checks out; it stays runtime-suspended until HPD.
- USB-C DisplayPort: DVO1 -> DP TX (`mediatek,mt8189-dp-tx`, a "v2" DP IP; mainline's `mtk_dp.c` doesn't cover it).
  [`mt8189-quigon-dp.dtsi`](../port/quigon/mainline/mt8189-quigon-dp.dtsi),
  [`mainline-mt8189-usbc-dp.patch`](../port/quigon/patches/mainline-mt8189-usbc-dp.patch): ChromeOS's
  `mtk_dp_v2.c` (+ HDCP-over-TEE files, MST stubbed: MT8189 has none) as `DRM_MEDIATEK_DP_V2`, DVO1 as
  `mt8189-dp-dvo` (no eDP FIFO settings, H front porch folded into the back porch). The EC does the alt-mode entry
  and muxing (UCSI) and drives the DP HPD pin (GPIO 27); EC GPIO 7 (`dp_aux_path_sel`) tells the DP TX which port.
  The DP PHY sits in the SSUSB power domain. ChromeOS's probe left a registered bridge pointing at freed memory
  whenever it deferred (the EC GPIO driver is a module): Hyprland oopsed in `detect`. The probe is devm-clean now.
- DT aliases (`ovl0/1`, `rdma0/1`, `dvo0/1`, `dsi0`) are required: mediatek-drm numbers blocks by alias, and
  without them OVL1/RDMA1 took OVL0/RDMA0's slots and the internal panel's CRTC stopped getting vblanks.

- OVL1/RDMA1 get their own IOMMU ports (larb0/larb1, as ChromeOS): the larbs translate every display port, so
  without them the external pipe would read through untranslated addresses.
- Audio: `PCM_0_BE` -> IT61620 and `TDM_DPTX_BE` -> DP TX (both hdmi-codec); the card gains "HDMI Jack" and
  "DP Jack".

Status (2026-10-10, a 4K monitor on HDMI): works. Hyprland extends the desktop at 3840x2160@30 (the IT61620 is an
HDMI 1.4 bridge: 4K tops out at 30 Hz, 1440p/1080p at 60). The first plug-in oopsed Hyprland's commit: mainline's
`mtk_crtc_update_output()` read `all_drm_private[crtc_index]`, an array indexed by mmsys, not CRTC; MT8189 has one
mmsys, so the second CRTC read past it
([`mainline-mtk-crtc-route-priv.patch`](../port/quigon/patches/mainline-mtk-crtc-route-priv.patch)).

USB-C DisplayPort works (2026-10-10, Dell U4025QW 40" 5120x2160 Thunderbolt monitor, on the monitor's Thunderbolt
upstream port): the EC/PDC negotiates PD (20 V / 3.25 A, 65 W, the Chromebook's maximum), swaps to DFP and enters
DP alt mode (`ectool usbpdmuxinfo`: USB=1 DP=1); mtk_dp_v2 trains the link and Hyprland extends the desktop at
2560x1080@60 (up to 3840x2160@30 and 2560x1440@60 offered; 5120x2160 is filtered: "dp timing not meet
alignment"). The monitor's USB hub enumerates through the same cable. DPMS off/on and an s2idle cycle with the
monitor attached both come back clean (the review fixes). First attempt failed on a charge-only USB-C cable:
the Chromebook saw only Type-C 5 V / 500 mA, PD "disabled", no DP, the PDC resetting ("Ping Status Error") — the
same under the ChromeOS kernel and after an EC cold reset; the monitor's own cable fixed it.

HDMI audio works (a 1 kHz tone through PipeWire, heard from the monitor and measured with a mic next to it):
- UCM: the HiFi verb routes DL2 to PCM 0 and adds an "HDMI" output (`hw:<card>,6`, jack "HDMI Jack"), so it shows
  in the sound menu while a monitor is plugged in.
- DP audio works too (2026-10-10, U4025QW): a "DisplayPort" output (UCM `HDMI2`, PCM 5 = the HDMI memif → TDM →
  DP TX, jack "DP Jack"). ChromeOS's profile switches `DPTX_OUT_MUX`/`DPTX_VIRTUAL_OUT_MUX`; mainline's AFE has
  neither, but routes the same path with its `TDM Playback Route` demux (`DPTXOUT`) and the `HDMI_CHn_MUX` channel
  map, which the UCM device sets. 1 kHz tone through PipeWire measured with a mic by the monitor.
- The IT61620 only takes 16/20/24-bit samples, but hdmi-codec offered S32_LE as well, and PipeWire picks the widest
  format: every start failed with `ASoC error (-22) at snd_soc_dai_hw_params() on i2s-hifi`, retried every 5 s
  (the Omarchy shell's audio model crashed once under that churn). 16-bit starts but plays garbled: the AFE's
  PCM 0 interface sends the same frame whatever the format (it never sets a word length), and only 24-bit lines up
  with it. The bridge now offers S24_LE only and PipeWire converts
  ([`mainline-it61620-audio-s24.patch`](../port/quigon/patches/mainline-it61620-audio-s24.patch)).
- The ELD reaches ALSA since def6 ([`mainline-it61620-eld.patch`](../port/quigon/patches/mainline-it61620-eld.patch): `get_eld` from the connector, refreshed after enable): `/proc/asound/card0/eld#*` shows the monitor (`DELL S2721QS`, LPCM 32/44.1/48 kHz, 16/20/24-bit). PipeWire's UCM sink keeps its UCM name ("HDMI").

### Default boot (2026-10-10)

Mainline is the default kernel now, with Omarchy on the ChromeOS kernel kept as the automatic fallback:

| Slot | Holds | Attributes |
|---|---|---|
| KERN-B (sda4) | mainline, [`quigon-kernel`](../port/quigon/root/usr/local/sbin/quigon-kernel) | priority above A and C, successful=0, tries=2 |
| KERN-C (sda6) | Omarchy on the ChromeOS kernel | successful=1, above KERN-A |
| KERN-A (sda2) | ChromeOS, untouched (its ROOT-A still serves `crossystem` and libmali) | |

- The firmware takes a try off KERN-B at every boot;
  [`boot-good`](../port/quigon/root/usr/local/libexec/quigon/boot-good) hands the two tries back once a boot reaches
  multi-user. A kernel that fails to come up twice in a row (hang, panic=10, the boot watchdog
  `mtk_wdt.start_timeout=31`) runs out of tries, and the firmware boots KERN-C. There, `quigon-kernel fallback`
  writes the previous mainline kernel back into KERN-B (the next reboot tries it), or turns KERN-B off when there
  is none. A kernel that boots but misbehaves isn't caught: `quigon-kernel restore previous` (or `off`) by hand.
- Test kernels ([`mainline-full.sh`](../scripts/mainline-full.sh), `quigon-test-kernel`) still boot once from
  KERN-B. The boot after one runs on KERN-C, which puts the default back (`kern-b` state `test <tag>`), so the
  reboot after that is mainline again.
- [`mainline-default.sh <tag>`](../scripts/mainline-default.sh) builds the tree with `LOCALVERSION=-<tag>`: a
  release of its own (`...-quigon-<tag>`), so the next test build (`...-quigon+`) can't overwrite the default's
  modules. It installs the modules, packs the FIT and runs `quigon-kernel install`, which keeps the old default as
  the rollback and prunes other `-quigon-<tag>` module trees.
- The cmdline finds root relative to the kernel slot, `root=PARTUUID=%U/PARTNROFF=3` (KERN-B + 3 = ROOT-C, as
  KERN-C's own `PARTNROFF=1`): a USB stick that probes first can't become sda.
- First default: `def1` (the external-display review fixes and HDMI audio below). Booted twice and passed a sleep
  test with HDMI connected.

**Fallback off (2026-10-10, later):** silently landing on the ChromeOS kernel (slower GPU through the libmali shims, no
external displays) was more confusing than useful, and a fallback nobody runs goes stale (the ufw trap above). Now
`quigon-kernel fallback-mode none` (`/etc/quigon/kernel-fallback`):
- KERN-B is marked successful after its first good boot (boot-good), so the firmware boots it every time; KERN-C
  has priority 0 and never boots on its own. Its ChromeOS kernel is kept in `/root/kern-backup/kern-c-chromeos.bin`.
- A newly installed default still gets two tries; if both fail the firmware falls through to ChromeOS itself
  (KERN-A), which can't be mistaken for the daily setup. Recovery: `quigon-kernel restore previous`, the SuzyQ, or
  the rescue USB stick.
- Test kernels (`quigon-test-kernel`, `mainline-full.sh`) go to KERN-C, tried once above KERN-B; the next boot is the
  default again (tested: test boot from KERN-C, then the default).
- `quigon-kernel fallback-mode chromeos` brings the automatic fallback back (restoring KERN-C's ChromeOS kernel from
  the backup if a test kernel overwrote it). `quigon-doctor` checks whichever mode is set.
- The login notification for a fallback boot (`quigon-kernel-notify`) is kept but didn't show on Omarchy 4's shell in
  the one test; moot without the fallback.

UCM fix found on the way: the DisplayPort route (`TDM Playback Route` = `DPTXOUT`) moved from the DP device's
EnableSequence into the verb. PipeWire opens every PCM when it probes the profile; after a reboot PCM 5 had no route,
failed ("no backend DAIs enabled for HDMI_FE"), and PipeWire dropped the whole profile (no speakers).

**UCM in alsa-ucm-conf's layout (2026-10-10):** the profile now lives in `ucm2/MediaTek/mt8189/rt1019p-rt5682s/`
(`conf.d/mt8189_1019_rt5/` links to it), shaped for upstream: every DPCM route in `init.conf`'s BootSequence (ALSA's
saved state keeps them across boots; PipeWire's ACP needs them before it probes the PCMs), the devices' switches in
`HiFi.conf`, HDMI and DisplayPort only if their jack controls exist. Tested from cleared routes (boot sequence →
4 outputs, 2 inputs) and after a reboot (speaker tone measured). Targets the mainline card: the ChromeOS kernel's
card names its DP routing differently (`DPTX_OUT_MUX`).

HDMI audio, second round: the IT61620's S24-only format list didn't reach PipeWire, because DPCM hands the FE
format (DL2 offers S32) to the BE unchanged, so every start still failed. The machine driver now pins PCM_0_BE to
S24_LE with a BE fixup, as it pins the DP BE to S32, and the AFE converts
([`mainline-mt8189-hdmi-audio-be-s24.patch`](../port/quigon/patches/mainline-mt8189-hdmi-audio-be-s24.patch)).
No WirePlumber rule needed.

USB-C DP review fixes ([`mainline-mt8189-dp-review-fixes.patch`](../port/quigon/patches/mainline-mt8189-dp-review-fixes.patch)),
from reading the code against ChromeOS (no DP monitor tested yet):
- ChromeOS's DP driver powered the DP TX off from a PM notifier at `PM_SUSPEND_PREPARE`, before mediatek-drm's
  `.prepare` disables the pipe (register writes into a powered-off block when suspending with a DP monitor in use).
  The notifier is gone; the ordinary dev_pm_ops run in the right order.
- Resume re-trains a sink that stayed plugged in (the port reset forgets it and no HPD edge follows; the bridge
  enable bailed out, a black external screen).
- NULL guards for a missing connector; mediatek-drm re-picks the external CRTC's output on every enable (a DPMS-off
  CRTC whose connector changed kept the old route); MT8189's mutex COLOR1 bit (4, RDMA0's, now 7).
- The DP PHY tuning in `mt8189-quigon-dp.dtsi` is Obiwan's (`mt8189-skywalker-obiwan.dts`), this board's family.
