# Desktop bring-up, 2026-10-08

## Hyprland on the built-in panel (software rendering)

- `pacman -Rdd linux-aarch64` first (the Arch kernel is never booted; ChromeOS's kernel is), then
  `pacman -Syu` and `hyprland foot seatd mesa noto-fonts ttf-jetbrains-mono-nerd libdrm wayland-utils`
  (Hyprland 0.56.2, Aquamarine 0.15.1, Mesa 26.2.4).
- Launcher: [`port/quigon/root/usr/local/bin/quigon-hyprland`](../port/quigon/root/usr/local/bin/quigon-hyprland),
  started by `quigon-desktop.service` as the desktop user (lingering enabled so `/run/user/1000` exists).
  Same software path as the phone: `LIBGL_ALWAYS_SOFTWARE=1 GALLIUM_DRIVER=llvmpipe GBM_ALWAYS_SOFTWARE=1`,
  `AQ_DRM_DEVICES=/dev/dri/card0 AQ_NO_MODIFIERS=1`, libseat through seatd.
- **seatd needs `SEATD_VTBOUND=0` on the daemon** (drop-in `seatd.service.d/novt.conf`). Without it seatd
  logs `Could not open device: client is not active` and `Could not open target tty`, and Aquamarine dies with
  `CBackend::create() failed!` (Hyprland exit 134). Setting it only in the client's environment is not enough.
- Result: Hyprland modesets eDP-1 (AU Optronics B140UAX01.2) at 1920×1200@60, the desktop and the onboarding
  tutorial show, foot opens. Idle CPU ~1%.
- Log noise that does not stop rendering: Aquamarine's `CDRMRenderer(drm): Can't create renderer, no matching
  devices found` / `Failed to update renderer state for eDP-1 on applyCommit` (its multi-GPU blit renderer
  can't find a GL device for mediatek-drm; Hyprland renders through its own llvmpipe EGL context).

## Omarchy packages

The official repo publishes aarch64 builds: `stable`/`rc` only carry apps (56 packages); **`edge` has the
desktop itself** (`omarchy 4.0.4`, `omarchy-settings`, `quickshell`, `walker`, `omarchy-keyring`, Omarchy's
Hyprland build). On aarch64 `omarchy` depends on `iwd` + `networkmanager` instead of the Limine/Snapper stack.

- `[omarchy] Server = https://pkgs.omarchy.org/edge/$arch` above `[core]`, key
  `40DFB630FF42BCFFB047046CF0134EE680CAC571` (Omarchy <pkgs@omarchy.org>) added from `omarchy.gpg` and lsigned.

## Omarchy session

- Desktop user created by [`scripts/setup-omarchy.sh`](../scripts/setup-omarchy.sh) (`DESKTOP_USER=…`), temporary
  password `omarchy`. It runs the parts of Omarchy's system setup that fit (theme-system, browser-policy,
  lockout limit, lockscreen PAM, ssh tweaks, bluetooth, regdom, udev, localdb) and skips
  `post-install/pacman.sh` (it copies Omarchy's **x86** `pacman.conf` + mirrorlist over Arch Linux ARM's),
  docker/snapper, and for now firewall + NetworkManager + SDDM.
- `omarchy-provision-user --first-install` fails in its default ISO context with
  `Error: bundled Node.js tarball missing from /opt/packages` (`user/mise-work.sh`). Running it with
  `OMARCHY_SETUP_CONTEXT=provision-owner` keeps first-install semantics (shipped migrations marked done) and falls
  back to `mise use -g node@latest` from the network (node 26.11.1 arm64).
- Session: `quigon-desktop@<user>.service` → [`quigon-omarchy`](../port/quigon/root/usr/local/bin/quigon-omarchy)
  → `uwsm start -g -1 -e -D Hyprland hyprland.desktop` (the Exec of Omarchy's `omarchy.desktop`).
- **uwsm needs a seat**: with no VT its env preloader fails `Could not determine foreground VT`
  (`/sys/class/tty/tty0/active` missing). Fix: `PAMName=login` plus `Environment=XDG_SEAT=seat0
  XDG_SESSION_TYPE=wayland XDG_SESSION_CLASS=user` in the unit, so pam_systemd creates a seat0 session and uwsm
  takes `XDG_SEAT`/`XDG_SESSION_ID` from it instead of looking up a VT.
- Result: `loginctl` shows a seat0 user session; Hyprland (start-hyprland watchdog), `omarchy-shell`
  (Quickshell), xdg-desktop-portal-hyprland, wireplumber, udiskie, monitor watch all start.
  `quickshell.network: … Could not find an available backend` until NetworkManager takes over Wi-Fi.

## Wi-Fi on NetworkManager

[`scripts/switch-to-networkmanager.sh`](../scripts/switch-to-networkmanager.sh) (run detached with
`CHECK_HOST=<laptop>`) writes a NetworkManager keyfile from the saved wpa_supplicant network
(`cloned-mac-address=permanent`, so DHCP keeps the same lease), stops `wpa_supplicant@wlan0` + networkd, starts
NetworkManager and waits up to 90 s for the check host. Online → retires the bring-up stack the way Omarchy's
`hardware/network.sh` does (networkd units disabled, wait-online units masked, NetworkManager enabled);
otherwise it rolls back. First real run: online after 45 s, same address.

- wpa_supplicant rewrites its config with **tab** indentation (`update_config=1`), so parse with `[[:space:]]*`.
- Omarchy 4.0.4 on aarch64 uses NetworkManager's default wpa_supplicant backend (`network.sh` disables iwd),
  even though the package depends on iwd.
- After the switch, `omarchy-restart-shell` brings the bar's network widget up (no more
  `quickshell.network: … Could not find an available backend`).
- Services Omarchy enables but only starts on the next boot (bluetooth, power-profiles-daemon, avahi, cups,
  oomd) can be started by hand.

## Boot defaults and the GPU safety net

- **USB is the default boot**: ChromeOS's own `crossystem` run from its read-only ROOT-A in a chroot (bind-mount
  `/dev /proc /sys /run /tmp` into `/mnt/cros`): `crossystem dev_default_boot=usb` (was `disk`). Harmless:
  `disable_power_management: Failed to open /run/lock/power_override/flashrom.lock`. The dev screen now boots the stick
  after its timeout; Ctrl+D still boots ChromeOS.
- **Boot-loop guard** ([`gpu-guard`](../port/quigon/root/usr/local/libexec/quigon/gpu-guard)): `quigon-gpu-guard.service`
  marks each GPU boot pending; `quigon-gpu-confirm.timer` (3 min after boot) clears it if Hyprland is running with libmali
  mapped. Two unconfirmed boots in a row → `gpu.env` renamed to `gpu.env.disabled-unstable` (session falls back to llvmpipe).
- Not silent: `quigon-gpu-notify` (autostart.lua `o.exec_on_start`) shows a critical notification at every login while the
  guard has the GPU off. [`quigon-gpu`](../port/quigon/root/usr/local/bin/quigon-gpu) `status|on|off` reports/flips the
  mode (takes effect at next login/boot).

## Swap: zram

At 3.6 of 7.9 GB used with Chrome, Grok Bot, Claude Code and Ghostty open, no swap. Added zstd zram swap the size of RAM
(`zram-generator`, [`zram-generator.conf`](../port/quigon/root/etc/systemd/zram-generator.conf), `zram` in
`modules-load.d`) with `vm.swappiness=100`, `vm.page-cluster=0`. ChromeOS's kernel has `CONFIG_ZRAM=m`, default lz4,
zstd available. No swap on the USB stick (slow, wears flash). It matters more here because there is no `CONFIG_MEMCG`, so
`systemd-oomd` can't run. Note: the first `systemctl start dev-zram0.swap` printed "unable to probe device: busy" but swap
came up (7.7G, prio 100); at boot the generator's units handle it.

## Low-memory protection (ChromeOS-style)

ChromeOS on this machine: 2× RAM zram (15.4G on 7.9G), MGLRU, `resourced` discarding Chrome tabs, renderers as preferred
OOM victims. Omarchy isn't a tab OS, so:

- **zram 2× RAM** (`zram-size = ram * 2`, zstd).
- **earlyoom 1.9.0** ([`/etc/default/earlyoom`](../port/quigon/root/etc/default/earlyoom)): SIGTERM at mem avail ≤ 5% and
  swap free ≤ 10% (SIGKILL at 2.5%/5%); `--prefer ^(chrome|grok-bot|electron)$` (Chrome's renderers carry the highest
  oom_score, so a tab goes first); `--avoid` compositor, bar, Xwayland, audio, network, session, SSH, terminals;
  `-N` [`earlyoom-notify`](../port/quigon/root/usr/local/libexec/quigon/earlyoom-notify) posts a critical notification
  naming what was closed.
- **MGLRU thrashing guard**: `lru_gen` is enabled (`0x0033`) but `min_ttl_ms` was 0; tmpfiles sets 1000 ms, so the kernel
  OOM-kills rather than thrash when the last second's working set can't stay resident.
- **Chrome Memory Saver** as a *recommended* policy (`/etc/opt/chrome/policies/recommended/quigon-memory.json`:
  `HighEfficiencyModeEnabled: true`, `MemorySaverModeSavings: 1`), user-changeable.
- **Revised the same day** after the user worried about losing typed work: on Linux Chrome gives *every* renderer
  `oom_score_adj` 300 (no foreground/background split like ChromeOS), and Grok Bot's UI renderer is 300 too. earlyoom now
  prefers only `chrome` and avoids `grok-bot`, `claude`, `nvim` as well. It stays as a last resort (≤5% RAM and ≥90% of
  15G zram used, where the alternative is a freeze followed by a kernel OOM kill of the same largest process); Chrome
  Memory Saver, which knows the active tab and skips tabs with form input, is the real protection.
  Disable entirely with `sudo systemctl disable --now earlyoom`.

## Battery panel

Same Omarchy bug as on the Zenbook A16: `omarchy-battery-status` picks the battery with `upower -e | grep BAT`, but here
UPower calls it `battery_sbs_10_000b` (smart battery `sbs-10-000b`, COSMX L25X3PG1, 58.7 Wh full / 55.3 Wh design), so the
power panel was empty. [`fix-omarchy-battery-status`](../port/quigon/root/usr/local/bin/fix-omarchy-battery-status) also
matches `/battery_`, reads cycles/thresholds from the found battery, and takes |W| in both the `power_now` and the
`current_now × voltage_now` branch (sbs has no `power_now` and reports current negative while discharging). A pacman hook
re-applies it after omarchy upgrades. Result: `Battery 88% · 10h 48m left · 4.7W / 58Wh`. Light use draws ~4.5–8.5 W.
- **Final decision (user):** no automatic killing at all, not even of a Chrome tab (could be mid-typing). earlyoom disabled
  (`systemctl disable --now earlyoom`; config kept in the repo) and the MGLRU `min_ttl_ms` guard reverted to 0 (it would
  make the kernel OOM-kill early). Remaining: 15.4G zstd zram and Chrome Memory Saver (discards background tabs, which
  reload; skips the active tab and tabs with form input; can be turned off in chrome://settings/performance). Trade-off:
  under extreme memory use the desktop can stall before the kernel's own OOM killer acts.
